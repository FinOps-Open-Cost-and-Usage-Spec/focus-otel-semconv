The registry defines no new signals. Its placement rules, a term this registry defines in [02-scope.md](../../02-scope.md), say where `focus.*` attributes go on signals OpenTelemetry already defines. None of them names a workload type; a workload such as "support bot" is only a value. Signal-specific rules are written as refinements in the model; see [FOCUS attributes on GenAI signals](gen-ai.md).

## Rules

1. **Billing scope of the emitting service goes on the OTel Resource.** When a process is itself a billed resource (a container service, a VM), its billing-scope keys go on its OTel Resource, so every span, metric, and log it emits carries them.
2. **Billing scope of a called service goes on the client span.** When a process calls a billed API or SaaS (a model provider, a managed database), that call's billing-scope keys go on the client span for the call, not on the caller's OTel Resource.
3. **Value-attribution IDs go on spans and travel in baggage.** `focus.workload.id`, `focus.task.id`, and `focus.outcome.id` MAY be set on any span doing work for a task, and SHOULD be propagated in OTel baggage so shared services (a central search index, a guardrail service) attribute their work to the caller. `focus.outcome.id` is optional, since outcomes are usually linked later. The GenAI workflow, agent, and tool spans are written as refinements that name where a task usually starts and what it calls; see [workflow, agent, and tool spans](gen-ai.md#workflow-agent-and-tool-spans).
4. **Only low-cardinality keys go on metrics.** Billing-scope keys and `focus.workload.id` MAY be set on metrics; the model lists them as `attributes.focus.metric_keys`. `focus.task.id` and `focus.outcome.id` MUST NOT be, since one value per task would create unbounded metric series.

## Service instance

Rule 1 is written as a refinement of the core `service.instance` entity. The `focus.*` attributes describe where the instance's own charge appears on the bill. They sit beside OpenTelemetry's `service.instance.cost_center.id` and `.name`, which record an internal allocation target such as a team or cost code; both may be set. `focus.workload.id` is not added here, because the caller sets the workload on each request and a shared instance serves many.

**[1] `service.instance.id`:** MUST be unique for each instance of the same `service.namespace,service.name` pair (in other words
`service.namespace,service.name,service.instance.id` triplet MUST be globally unique). The ID helps to
distinguish instances of the same service that exist at the same time (e.g. instances of a horizontally scaled
service).

Implementations, such as SDKs, are recommended to generate a random Version 1 or Version 4 [RFC
4122](https://www.ietf.org/rfc/rfc4122.txt) UUID, but are free to use an inherent unique ID as the source of
this value if stability is desirable. In that case, the ID SHOULD be used as source of a UUID Version 5 and
SHOULD use the following UUID as the namespace: `4d63009a-8d0f-11ee-aad7-4c796ed8e320`.

UUIDs are typically recommended, as only an opaque value for the purposes of identifying a service instance is
needed. Similar to what can be seen in the man page for the
[`/etc/machine-id`](https://www.freedesktop.org/software/systemd/man/latest/machine-id.html) file, the underlying
data, such as pod name and namespace should be treated as confidential, being the user's choice to expose it
or not via another resource attribute.

For applications running behind an application server (like unicorn), we do not recommend using one identifier
for all processes participating in the application. Instead, it's recommended each division (e.g. a worker
thread in unicorn) to have its own instance.id.

It's not recommended for a Collector to set `service.instance.id` if it can't unambiguously determine the
service instance that is generating that telemetry. For instance, creating an UUID based on `pod.name` will
likely be wrong, as the Collector might not know from which container within that pod the telemetry originated.
However, Collectors can set the `service.instance.id` if they can unambiguously determine the service instance
for that telemetry. This is typically the case for scraping receivers, as they know the target address and
port.

**[2] `focus.billing_account.id`:** When the instance is a billed resource and the value is known from configuration.

**[3] `focus.billing_account.id`:** OpenTelemetry has no billing-account concept. BillingAccountId is
unique within the invoice issuer, not the service provider, and is
usually supplied by configuration rather than detected at runtime.

Joins on this attribute assume a direct purchase, where the invoice
issuer is the service provider. For marketplace purchases the bill
carries the marketplace's billing account, which telemetry cannot know.

**[4] `focus.resource.id`:** `cloud.resource_id` identifies the monitored resource, which can differ
from the billed one: an Azure function rather than its function app, a
Lambda ARN that includes a version, or ECS telemetry that names a task,
container, or instance. This attribute MUST carry the billed resource.

Leave this attribute unset when the charge is not tied to a resource,
such as pay-per-token model usage.

**[5] `focus.service.name`:** This is not OpenTelemetry's `service.name`, which names the emitting
application. When a charge is not tied to a resource, as with
pay-per-token model APIs, the service is the finest billing-scope key
after the model.

**[6] `focus.service_provider.name`:** Set this when telemetry describes work billed by a known service provider.
Unlike `cloud.provider`, which is a fixed list of cloud provider IDs, this
attribute accepts any provider, including SaaS and data-center providers,
and its value MUST equal the bill exactly.

ResourceId is unique only within a service provider, so joins on
`focus.resource.id` also require this attribute.

**[7] `focus.sub_account.id`:** When the instance's charge is related to a sub account.

**[8] `focus.sub_account.id`:** A sub account is the account a resource belongs to, such as an AWS member
account, an Azure subscription, or a GCP project. This is the same level
as `cloud.account.id`.

**Open question:** this attribute may be deprecated in favor of
`cloud.account.id` if OpenTelemetry can guarantee bill-exact values
across all providers, including SaaS.

**[9] `service.instance.cost_center.id`:** The cost center identifier enables tracking and attribution of service resource costs to organizational units, billing accounts, or teams. It is typically a string identifier such as a billing account ID, cost allocation code, or internal accounting ID.

## Cloud

For a cloud-hosted resource, the same keys are also written as a refinement of the core `cloud` entity, so each `focus.*` key sits beside the `cloud.*` attribute nearest to it. The note on the refinement gives the reason each is not reused. This refinement is a proposal for discussion with the OpenTelemetry Semantic Conventions (SemConv) SIG: wherever a `cloud.*` value can be guaranteed to equal the bill, the `focus.*` key would be deprecated in its favor in a later release. Until then, every `focus.*` key is set even when its value matches the `cloud.*` attribute, so consumers can depend on it.

| `focus.*` key | Nearest `cloud.*` attribute | Why it is not reused |
|---|---|---|
| `focus.service_provider.name` | `cloud.provider` | A fixed list of IDs such as `aws`; the bill uses the provider's name, and FOCUS covers SaaS and data-center providers too |
| `focus.billing_account.id` | None | `cloud.*` has no account the bill is issued to, such as an AWS management account |
| `focus.sub_account.id` | `cloud.account.id` | The same level, but not yet shown to equal SubAccountId for every provider |
| `focus.resource.id` | `cloud.resource_id` | The monitored resource, which can differ from the billed one, such as a Lambda ARN with a version |
| `focus.service.name` | `cloud.platform` | A fixed list of IDs such as `aws_ecs`; the bill uses the service's name, such as Amazon Elastic Container Service |

Set these only when the resource's own charge appears in FOCUS Cost and Usage data.

## When IDs are known

The rules assume an ID is known when the span is created. That holds for some IDs and not others.

- **`focus.workload.id`:** almost always known at runtime, since the caller sets it from configuration and propagates it in baggage.
- **`focus.task.id`:** usually known at runtime, because it is typically an existing business key such as a ticket, pull request, or job ID. When it is not, it is linked afterward by mapping an attribute the span already carries, such as the trace ID or a business key, to the task in the Task dataset.
- **`focus.outcome.id`:** often not known at runtime, because outcomes are verified later, such as a deflection confirmed days afterward or a pull request that survives its SLA window. It is linked through the Task dataset, which records each task's OutcomeId.

Linking after the fact means joining downstream, not editing telemetry. Exported spans cannot change, so late links are made at ingest, through Collector or backend enrichment from a lookup, or in the Telemetry dataset. Spans that are never linked roll up as `UNLINKED_SCRAP`.

The practical minimum at runtime is therefore `focus.workload.id` and `focus.task.id`. `focus.outcome.id` is needed on spans only for a direct path from telemetry to outcomes, used when a team does not track tasks.

## From telemetry to the Telemetry dataset

Spans are not joined to the bill one by one. They are aggregated into the Telemetry dataset, proposed for FOCUS 1.6 in the companion specification, which joins to cost, tasks, and outcomes.

- **Grain:** leaf inference and tool spans are rolled up into hourly or daily windows, and span and trace IDs are dropped.
- **Keys:** each row is grouped by the billing-scope keys, the model, and the value-attribution IDs, over a window aligned to the FOCUS charge period.
- **Measures:** traces are usually sampled and metrics are not, so exact usage totals come from metrics labeled by workload and billing scope, while sampled spans supply per-task proportions.
- **Joins:** rows join to Cost and Usage on the billing-scope keys and charge period, and to Task and Outcome on `focus.task.id` and `focus.outcome.id`. EffectiveCost is then apportioned across the tasks sharing a scope.
- **Unlinked work:** spans with no task ID roll up with TaskId and OutcomeId set to `UNLINKED_SCRAP`, so all cost still reconciles.

Weighting and apportionment formulas are out of scope for this registry. They belong to the companion specification.
