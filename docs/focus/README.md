## Purpose

`focus.*` is a small, cross-cutting set of attributes that lets any telemetry be joined to charges in the FOCUS Cost and Usage dataset, and from there to the Task, Outcome, and Value datasets of the FOCUS companion specification *Value Attribution Data Architecture: Schema and Explainer* (v0.1.4).

The registry carries join keys only: the values telemetry needs to find its charge or its task. Region, price, cost, and quantities come from the charge once the join is made. Usage measurements, such as token counts, stay in the domain conventions that already define them, such as `gen_ai.*`.

## Terminology

A `focus.*` attribute carries the value of a FOCUS column on an OpenTelemetry signal. It has nothing to do with FOCUS Attributes, which are sets of requirements in the FOCUS specification. An OTel Resource (the service emitting telemetry) is not a FOCUS Resource (the billed item that ResourceId identifies). The [placement rules](placement.md) are this registry's rules for which signals carry which `focus.*` attributes; the term is its own, not OpenTelemetry's. See [02-scope.md](../../02-scope.md) for the full terminology, and [OpenTelemetry concepts](otel-concepts.md) for OTel terms such as span, refinement, and attribute group.

## Cost and Usage scope

These attributes locate a telemetry record's charge. The placement rules call them the billing-scope keys, and the model groups them as `attributes.focus.billing_scope`. FOCUS references are to FOCUS 1.4 unless noted, and are also recorded in each attribute's `annotations.focus` in the model.

| Attribute | FOCUS column (section) | Nearest OTel attribute | Decision |
|---|---|---|---|
| [`focus.service_provider.name`](/docs/registry/attributes/focus.md) | ServiceProviderName (3.1.54) | `cloud.provider`, a fixed list of cloud providers | Define |
| [`focus.billing_account.id`](/docs/registry/attributes/focus.md) | BillingAccountId (3.1.8) | None | Define |
| [`focus.sub_account.id`](/docs/registry/attributes/focus.md) | SubAccountId (3.1.62) | `cloud.account.id`, same level | Open: reuse if bill-exact |
| [`focus.resource.id`](/docs/registry/attributes/focus.md) | ResourceId (3.1.51) | `cloud.resource_id`, the monitored rather than billed resource | Open: define unless OTel adds a billing-level identifier |
| [`focus.service.name`](/docs/registry/attributes/focus.md) | ServiceName (3.1.56) | `service.name`, a different concept | Define |
| `gen_ai.response.model` | SkuPriceDetails.ModelId (FOCUS 1.5; a first-class ModelId is proposed for 1.6) | Itself | Reuse; not a `focus.*` attribute |

Every join starts from the provider and billing account. Each charge then has at most one finer key:

- the **resource**, when the charge is tied to one;
- the **model**, for pay-per-token usage, where ResourceId is null; or
- **neither**, as with a support plan or SaaS seat, where the join stops at the service and its cost is shared across all telemetry in that scope.

**[1] `focus.billing_account.id`:** OpenTelemetry has no billing-account concept. BillingAccountId is
unique within the invoice issuer, not the service provider, and is
usually supplied by configuration rather than detected at runtime.

Joins on this attribute assume a direct purchase, where the invoice
issuer is the service provider. For marketplace purchases the bill
carries the marketplace's billing account, which telemetry cannot know.

**[2] `focus.resource.id`:** `cloud.resource_id` identifies the monitored resource, which can differ
from the billed one: an Azure function rather than its function app, a
Lambda ARN that includes a version, or ECS telemetry that names a task,
container, or instance. This attribute MUST carry the billed resource.

Leave this attribute unset when the charge is not tied to a resource,
such as pay-per-token model usage.

**[3] `focus.service.name`:** This is not OpenTelemetry's `service.name`, which names the emitting
application. When a charge is not tied to a resource, as with
pay-per-token model APIs, the service is the finest billing-scope key
after the model.

**[4] `focus.service_provider.name`:** Set this when telemetry describes work billed by a known service provider.
Unlike `cloud.provider`, which is a fixed list of cloud provider IDs, this
attribute accepts any provider, including SaaS and data-center providers,
and its value MUST equal the bill exactly.

ResourceId is unique only within a service provider, so joins on
`focus.resource.id` also require this attribute.

**[5] `focus.sub_account.id`:** A sub account is the account a resource belongs to, such as an AWS member
account, an Azure subscription, or a GCP project. This is the same level
as `cloud.account.id`.

**Open question:** this attribute may be deprecated in favor of
`cloud.account.id` if OpenTelemetry can guarantee bill-exact values
across all providers, including SaaS.

## Value scope

These attributes link a telemetry record to the work it served. The placement rules call them the value-attribution IDs, and the model groups them as `attributes.focus.value_attribution`.

| Attribute | Links to | Known at runtime? | On metrics? | Decision |
|---|---|---|---|---|
| [`focus.workload.id`](/docs/registry/attributes/focus.md) | All datasets, for portfolio rollups | Almost always, from the caller's configuration, then propagated in baggage | Yes | Define, pending review by the OpenTelemetry Semantic Conventions (SemConv) SIG |
| [`focus.task.id`](/docs/registry/attributes/focus.md) | Task dataset | Usually, as an existing business key | No | Define |
| [`focus.outcome.id`](/docs/registry/attributes/focus.md) | Outcome dataset, and Value through it | Often not; linked later through the Task dataset | No | Define; optional on spans |

Value itself is never part of telemetry. It is reached through Outcome, in the Value dataset.

**[1] `focus.outcome.id`:** Outcomes are often verified after the telemetry is emitted, such as a
deflection confirmed days later. When the outcome is not known at
runtime, leave this attribute unset; the link is made through the Task
dataset, which records each task's OutcomeId.

This attribute MUST NOT be set on metrics.

**[2] `focus.task.id`:** A task is the unit of work that cost is apportioned to, such as a support
ticket, pull request, or batch job. It is usually an existing business key
known at runtime.

This attribute MUST NOT be set on metrics, since one value per task
would create unbounded metric series.

**[3] `focus.workload.id`:** A workload may span many services and share services with other
workloads. It differs from `service.name` (one deployed application),
`service.namespace` (fixed per service on the Resource) and a Kubernetes
workload (one deployment), because the caller sets it from configuration on
each request and propagates it in baggage, so that shared services
attribute their work to the caller.

This attribute is low-cardinality and MAY be set on metrics.

## Naming

Take the FOCUS column, split off its final property word (Id, Name) as the last segment, and write the rest in snake_case: `BillingAccountId` becomes `focus.billing_account.id`. Anyone who knows FOCUS can predict the attribute name.

OpenTelemetry spells `cloud.resource_id` with an underscore but `cloud.account.id` with a dot. `focus.resource.id` follows the dotted `{object}.{property}` form in OpenTelemetry's current naming guidance.

## Reuse decisions

The registry reuses an OpenTelemetry attribute wherever its meaning and its values match the bill, and defines a `focus.*` attribute only where they do not:

1. **Reuse** when the concept and the values match (`gen_ai.response.model`).
2. **Define** a distinct attribute when the word matches but the concept differs (`focus.service.name`).
3. **Negotiate** with the SemConv SIG when the concept matches but the scope or format differs (`focus.sub_account.id`, `focus.resource.id`).

The obstacle in the third case is exactness, not the `cloud.*` namespace, which is already used for private data centers. FOCUS covers SaaS and licensing as well as infrastructure, and its values must equal the bill exactly. Where a `cloud.*` attribute can guarantee that, FOCUS reuses it and deprecates the `focus.*` attribute, so providers emit one attribute rather than two. The [cloud refinement](placement.md#cloud) sets each `focus.*` key beside its nearest `cloud.*` attribute, so the case for each can be judged side by side.

For `focus.workload.id`, the closest OpenTelemetry concept is `service.namespace`. It sits on the OTel Resource, so each service has exactly one, and it cannot attribute a shared service's work to the workload that called it. `gcp.apphub.workload.id` is specific to GCP and names a compute unit, and `gen_ai.agent.*` identifies a single agent.

Core OpenTelemetry also defines `service.instance.cost_center.id` and `.name`, whose description mentions a billing account ID as one possible value. They record an internal allocation target, chosen by the organization. The `focus.*` billing-scope keys record where a charge appears on the bill, chosen by the invoice issuer, so both are kept.

Left out entirely, because the join does not need them: region and availability zone; charge period; quantities and units; costs; SKU and pricing columns other than the model; host provider; and invoice issuer.

## Open questions

For the FOCUS Working Group:

- Graduate ModelId from SkuPriceDetails to a first-class Cost and Usage column in 1.6.
- Until then, require SkuPriceDetails.ModelId whenever a charge is for model usage.
- Exports that follow FOCUS 1.2, including [AWS's](providers/aws.md), carry ProviderName, which ServiceProviderName replaced in 1.3. Document how joins on `focus.service_provider.name` fall back to ProviderName until those exports move to 1.3 or later.
- Define model values as the exact model string the provider's API returns, matching `gen_ai.response.model`.
- Document that billing-account joins assume a direct purchase. For marketplace purchases the bill carries the marketplace's billing account, which telemetry cannot know, so the join falls back to provider and service.
- Decide whether a changed meaning always requires a new attribute, or whether `development` attributes may still change as OpenTelemetry allows.

For the SemConv SIG:

- Can `cloud.account.id` and `cloud.resource_id` guarantee bill-exact values across non-cloud providers? For each key in the [cloud refinement](placement.md#cloud), would the SIG rather widen the `cloud.*` attribute than have FOCUS define its own?
- Is `service.namespace` meant to carry a workload in FOCUS's sense, or is a request-scoped `focus.workload.id` acceptable?
- Which parts belong in the core conventions now, rather than starting federated?
- Which signal-specific rules should be formalized first with the GenAI SIG?
- If task and outcome data is ever reported through OpenTelemetry, such as task-completed or outcome-verified events, those would be new signals. Which SIG would own them?
- How does an outside registry get onto OpenTelemetry's planned list of federated registries, and who approves listings?
- Should `service.instance.cost_center.id` stay an internal allocation target, distinct from the bill-exact `focus.billing_account.id`?
