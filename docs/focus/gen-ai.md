## Inference span

The inference span is a client span for a billed call, so it carries the called service's billing scope (rule 2) and the value-attribution IDs (rule 3). For pay-per-token usage `focus.resource.id` is unset, and `gen_ai.response.model` is the finest join key.

**Status:** ![Development](https://img.shields.io/badge/-development-blue)

Adds FOCUS billing-scope keys and value-attribution IDs to the GenAI inference client span, so each model call can be joined to its charge and to the task it served.

**Span kind** SHOULD be `CLIENT` and MAY be set to `INTERNAL` on spans representing
call to models running in the same process. It's RECOMMENDED to use `CLIENT` kind
when the GenAI system being instrumented usually runs in a different process than its
client or when the GenAI call happens over instrumented protocol such as HTTP.

One client request may involve multiple server-side inference operations.
The model provider or server, when instrumented, may record those operations
as nested inference spans.

Telemetry consumers should group inference spans by [`service.name`](https://opentelemetry.io/docs/specs/semconv/registry/entities/service/)
when counting operations or tokens.

**Span status** SHOULD follow the [Recording Errors](https://opentelemetry.io/docs/specs/semconv/general/recording-errors/) document.

## Workflow, agent and tool spans

Workflow, agent and tool spans are not billed calls, so they carry no billing scope. They carry the value-attribution IDs (rule 3). A workflow or agent span is usually where a task starts, so it is the natural place to set `focus.task.id`; baggage then carries the IDs to the inference and embeddings calls beneath it. A call to a remote agent carries the IDs so the remote agent's work is attributed to the caller's task.

**[3] `gen_ai.conversation.id`:** Instrumentations SHOULD populate conversation id when they have an identifier
for the conversation readily available for a given operation, for example:

- when the client framework being instrumented manages conversation history
(see [LlamaIndex chat store](https://docs.llamaindex.ai/en/stable/module_guides/storing/chat_stores/),
[LangChain `session_id`](https://reference.langchain.com/python/langchain-core/runnables/history/RunnableWithMessageHistory),
and [Google ADK sessions](https://adk.dev/sessions/session))
- when instrumenting GenAI client libraries that maintain a conversation on the backend
(see [AWS Bedrock agent sessions](https://docs.aws.amazon.com/bedrock/latest/userguide/agents-session-state.html),
[OpenAI Assistant threads](https://platform.openai.com/docs/api-reference/threads))

When no identifier for the conversation is available, instrumentations SHOULD NOT
populate conversation id. For example, a new UUID, a trace identifier, or a hash
of request content SHOULD NOT be used as a fallback value.

Application developers that manage conversation history MAY add conversation id to GenAI and other
spans or logs using custom span or log record processors or hooks provided by instrumentation
libraries.

**[6] `focus.task.id`:** A task is the unit of work that cost is apportioned to, such as a support
ticket, pull request or batch job. It is usually an existing business key
known at runtime.

This attribute MUST NOT be set on metrics, since one value per task
would create unbounded metric series.

**[7] `focus.workload.id`:** A workload may span many services and share services with other
workloads. It differs from `service.name` (one deployed application),
`service.namespace` (fixed per service on the Resource) and a Kubernetes
workload (one deployment), because it is set per request and propagated
in baggage so that shared services attribute their work to the caller.

This attribute is low-cardinality and MAY be set on metrics.

**[9] `gen_ai.tool.type`:** Extension: A tool executed on the agent-side to directly call external APIs, bridging the gap between the agent and real-world systems.
  Agent-side operations involve actions that are performed by the agent on the server or within the agent's controlled environment.
Function: A tool executed on the client-side, where the agent generates parameters for a predefined function, and the client executes the logic.
  Client-side operations are actions taken on the user's end or within the client application.
Datastore: A tool used by the agent to access and query structured or unstructured external data for retrieval-augmented tasks or knowledge updates.
